# Singularity Browser — guardrails for every session

A native macOS browser whose organising unit is the **Space**. The sidebar holds three kinds of tabs side by side: **web pages**, **terminals** (where the user's own coding agents run), and **locally generated HTML artifacts**. An *external* agent (e.g. Claude Code in a terminal tab) can drive the browser through an MCP server the app exposes. There is no built-in AI, no chat UI, no API keys.

## The scope rule
**If it is not a tab type, it is not in v1.**

If you want to add something that is not in the brief, write it to `IDEAS.md` under "New, not yet decided" instead of building it. Ask before adding any dependency not listed below.

## Explicitly out of scope for v1
Do not build, scaffold, or leave TODOs for:
sync of any kind · browser extensions (WebExtensions/WKWebExtension; Singularity plugins replace them) · built-in AI or chat UI (AI only inside plugins, round 2) · Windows/Linux/iOS · Peek windows for links clicked inside Singularity · bookmarks beyond pinned tabs and folders · history UI beyond what the command palette needs · reader mode · ad blocking · themes · API routes on the artifact server · databases · an entity store · calendar/email/notes integration · agent orchestration (Herdr already does that; we only host terminals).

**Scope change (owner decision, after Phase 4):** tiling / split view is *in* v1, built before Phase 5: nested splits (any pane splits right or down), Arc-style split groups, created via context menu, drag and drop, keyboard and palette.

**Scope change (owner decision, plugins round 1):** Singularity plugins (not a tab type) are in v1; see the spec (`docs/superpowers/specs/2026-11-09-plugins-design.md`).

**Scope change (owner decision, 2026-11-11):** projects in a Space (not a tab type) are in v1: a Space lists named folders, and a new terminal starts in one; see the spec (`docs/superpowers/specs/2026-11-11-projects-design.md`).

**Scope change (owner decision, 2026-11-10):** everything listed in `IDEAS.md` is approved to be built, except its sections "Decided against" and "New, not yet decided". `IDEAS.md` has the order and the rules (projects need an owner-approved design first; small items don't). Where an approved item overlaps the out-of-scope list above (e.g. the plugin storage API, download UI), the item in `IDEAS.md` wins; the rest of the list still holds.

**Scope change (owner decision, 2026-11-12):** the agent inbox is in v1 (spec `docs/superpowers/specs/2026-11-11-agent-inbox-design.md`). It is not orchestration: it starts, assigns and keeps nothing; it only shows what hosted terminals and the browser's own approval step report, and lets the owner answer.

**Scope change (owner decision, 2026-11-12):** little windows are in: a link clicked in another app opens in its own throwaway window, from which it can be opened in a Space (`docs/superpowers/specs/2026-11-12-little-window-design.md`). With it, Singularity can be the default browser (release builds only). Not a tab type, and still out: Peek for links inside Singularity, a setting to skip the little window.

**Scope change (owner decision, 2026-11-13):** the Assistant is in, in three parts, each with its own design first (part 1: `docs/superpowers/specs/2026-11-13-assistant-part1-design.md`). It is a bundled plugin (`Plugins/assistant/`), so the AI lives in a plugin, not in the app: removing it leaves no AI in Singularity. The owner's decisions: the plugin is the face, and the existing agent door, `singularity-mcp`, will be its hands in part 2 (the same tools, Space policy, approvals and agent log as any outside agent; no second way into the browser); its page is TSX that the plugin ships, shown in a native frame (a panel at the right of the window, or a plugin tab); it runs the user's own installed, signed-in `claude`, and Singularity shows no login and never touches a token or key; in part 3 it may type into a terminal only after the owner approved the exact text, every time, which lifts "no agent orchestration" for the Assistant only, and only in part 3. It is named Assistant ("agent" stays the word for outside agents, and no string calls the Assistant one); other providers (Codex and others) may come later. Part 1 is built: a plugin's own page in a panel or tab, one running program per plugin, and a plain streaming chat with no tools.

**Scope change (owner decision, 2026-11-13):** the sidebar work is in (spec `docs/superpowers/specs/2026-11-13-sidebar-design.md`): launcher buttons that open a terminal with a command typed in, an emoji per Space, a sidebar that can be resized and hidden, agent activity moved to Settings. None is a tab type. A launcher is not orchestration: it types the owner's own command once and starts, assigns and watches nothing.

## Hard constraints
- Swift + SwiftUI (AppKit where SwiftUI falls short). No Electron, no web-based app chrome.
- WKWebView only. macOS 14+, Apple Silicon first.
- No sync, accounts, telemetry. All data lives under `~/Singularity/`.
- Allowed dependencies: SwiftTerm (terminal), FlyingFox or Hummingbird (local HTTP server), the official MCP Swift SDK, Sparkle 2 (self-update; pinned to an exact version in `Package.swift`, owner-approved 2026-11-12). Verify APIs before use; do not rely on memory.
- Boring, readable Swift. The owner reads TypeScript/PHP more fluently than Swift, so comment the non-obvious AppKit/WebKit parts.

Key decisions:
- **Space** = UUID, name, colour, slug (fixed at creation; renaming changes only the display name; the one exception is the welcome flow, see Onboarding), cwd. Each Space has its own `WKWebsiteDataStore(forIdentifier: space.id)`, so cookies and storage are isolated.
- **Not sandboxed.** Terminal tabs need to spawn login shells. Hardened runtime is on.
- On disk: `~/Singularity/state.json` (Space order and selection) and `~/Singularity/spaces/<slug>/{space.json, history.jsonl, favicons/}`. Writes are atomic and debounced.
- **Known exception to "everything under ~/Singularity/":** each Space's cookies, logins and site data live in WebKit's store at `~/Library/WebKit/dev.roosa.Singularity/WebsiteDataStore/<space id>/`. WebKit chooses that location and the app cannot move it. Consequences: copying `~/Singularity/` does not carry logins over; deleting `~/Singularity/` by hand leaves the cookies behind (deleting a Space in the app does remove them); and the stores are tied to the bundle ID, so **never change `dev.roosa.Singularity`**, or every Space starts logged out. Changing the signing identity is fine.
- **Artifact server auth (decided with the owner; the brief asked for a Bearer header on every request).** WebKit cannot add headers to page sub-requests, so: the app loads each artifact tab's first request with `Authorization: Bearer <token>`; the server answers that with `Set-Cookie: singularity_token=…; HttpOnly; SameSite=Strict`; sub-requests and `fetch()` then use the cookie. The token is random per Space per launch, never in files, never readable by page JS, and the cookie lives only in that Space's WebKit store. (Setting the cookie natively via `WKHTTPCookieStore` does not work: WebKit silently drops cookies for a bare-IP domain.) The server also refuses non-loopback Host headers (DNS rebinding) and sends no CORS headers.
- `window.singularity` exists only on the Space's artifact origin (the script checks `location.origin`, and the native handler checks the message's `securityOrigin`). `prompt()` always asks (an inbox approval entry showing the text), then bracketed-pastes into the Space's most recently used running terminal and presses Return. Phase 5 replaces "always ask" with the Space policy.
- **MCP.** Agents run `Singularity.app/Contents/MacOS/singularity-mcp` (stdio). It contains no MCP logic: the app runs an MCP `Server` (official Swift SDK) per socket connection, reusing the SDK's `StdioTransport` on the socket's file descriptor. Tools: `list_spaces` plus `<slug>.<tool>` for Spaces with `agentsEnabled` (per-Space toggle in Edit Space, off by default); `tools/list_changed` is sent when that set changes. Claude Code shows `work.read_page` as `mcp__singularity__work_read_page` (dots become underscores; verified). The socket folder is 0700, the socket 0600, and peers must have the same uid.
- **Page agent.** `PageAgentScript` is injected at document start into every web/artifact tab in an isolated `WKContentWorld`, so pages can't see or tamper with it. Refs come from a WeakMap (element → number) and are stable for the life of a page load. Everything page-derived that is returned to an agent goes through `UntrustedContent.wrap`. Agent-opened tabs load in the background (not selected) at 1280×800.
- **Approvals (Phase 5).** Every agent tool call and every `window.singularity.prompt()` goes through `AgentApprovals.check` *inside the app*, so the policy holds for any client (an agent once drove `singularity-mcp` directly). Rules live in `AgentApprovalRules` (Core, tested): reads always pass; readOnly refuses acting; allowAll passes; ask creates an inbox entry (Allow / Allow on <site> / Deny, plus Show Tab, which answers nothing and restarts the clock; unanswered after the timeout = denied, logged `timeout`) unless the page's site was allowed, and **always** asks for form submissions, artifact prompts and going to a site not yet allowed. The inbox replaced the old `NSAlert` sheet; `AgentApprovalRules` did not change. Several requests can wait at once, each with its own deadline, so three safeguards came with it: answer buttons ignore clicks for 0.5 s after the panel appears or a card is added, removed or moved (`InboxCenter.answerLockout`: a double-click's second click must not land on the next card's Allow; the same lock covers Claude Code's cards: question options, Send, and a permission's Allow / Deny); at most 5 approvals wait per Space, one more is denied at once (`maxWaitingApprovalsPerSpace`: a page looping `prompt()` can't flood); and an answer is re-checked against the Space's *current* policy, so an Allow given after the Space went read-only or was deleted becomes a deny. "Allow on <site>" also releases other waiting requests of that site in that Space that the rules now pass (never the always-ask ones). Arriving while Singularity is active, an approval opens the panel by itself without taking the keyboard; in the background: banner and one Dock bounce. `click` inspects the element first (submits a form? link to another site?), and while a click/type runs `WebTabController.agentNavigationGuard` holds any navigation that wasn't approved. Every call is appended to `<space>/agent-log.jsonl` (password text never logged) and shown per Space in Settings → Agents → "Activity…" (it was a sidebar pane until 2026-11-13); tabs opened by agents carry `openedByAgent` (sparkles badge), tabs being worked on pulse. The approval timeout is a setting (`agentApprovalTimeoutSeconds` in `~/Singularity/settings.json`); set it to e.g. 5 for tests.
- **Agent inbox** (spec `docs/superpowers/specs/2026-11-11-agent-inbox-design.md`; its "As tested" and "As built" sections override the design). One list, across all Spaces, of agents waiting for the owner or done, plus browser approvals: a tray button at the top of the Space rail (count; each Space circle its own count), a panel beside it (⌃⌘I, Show Inbox in the menu and palette), macOS banners and the Dock badge (`InboxNotifier`). Every rule is in Core `Inbox` (pure, tested); `InboxCenter` feeds it. Things to keep:
  - **Nothing is saved**, no history; log lines carry kinds, tab ids and counts, never agent text. Everything an agent or page puts in an entry is untrusted: `InboxText.clean` / `cleanBlock`, shown with `Text(verbatim:)`. **No inbox button is ever a default button**, and the panel is a non-activating `NSPanel` (a SwiftUI popover takes key focus): opened by the app itself it never takes the keyboard, so Return or Space typed into a terminal can't press Allow. It becomes key only when the owner opened it (tray, ⌃⌘I, palette) while the app is active.
  - **Level 1, any agent, no setup:** SwiftTerm's OSC 7501 status records (Claude Code sends them only after the terminal answers its `7501;?` probe, which SwiftTerm does; SwiftTerm also decodes the base64 `msg`), OSC 9/777 notifications, and the bell (only with a program other than the shell in front). OSC 9/777 are read through `observeOscEvents`: registering a handler for 9 would replace SwiftTerm's own, which is what reads `9;4` progress reports. At most one level-1 entry per tab; a tab that sends status records is trusted over its bells and notifications. With several records in a tab (Claude Code keeps some for subagents and tasks) one speaks for it: blocked > error > working > done > idle (`InboxRules.summarise`; working above done, so a finished subagent doesn't make a busy tab look done). A level-1 entry hidden behind a held request of its tab is not announced (no second banner).
  - **Looked at vs went to.** "Looked at" (app active, window key, tab on screen: `InboxRules.isLookedAt`) is checked once, on arrival: then no entry is made and a hook gets "no decision" at once, so the prompt shows in the terminal as before. After that only *going* there removes an entry: selecting the tab, its split or its Space, Go to terminal, or clicking or typing in the terminal. The app merely becoming active again does not (the owner must still find the entry after clicking a banner). Typing is seen through one app-wide `NSEvent` key monitor, because SwiftTerm's `keyDown` is `public`, not `open`; ⌘-keys are skipped (⌘1…9, ⌘T and ⌃⌘I are commands, not typing).
  - **Level 2, Claude Code with the hook.** `Contents/MacOS/singularity-hook` (no dependencies, not even Core) is Claude Code's command hook for `PreToolUse` (matcher `AskUserQuestion`), `PermissionRequest` and `Stop`. It reads `SINGULARITY_TAB` (the tab's id) and `SINGULARITY_HOOK_SOCKET` (`<root>/.run/hook.sock`), which terminal tabs export next to `SINGULARITY_SPACE` and pass through `hc run` (a herdr shell started before this feature has neither and stays at level 1), sends one line and prints the app's reply. Either variable missing, or nobody listening: no output, exit 0, at once; it never starts the app. It always reads all of stdin first, even when it then does nothing: exiting without reading makes Claude Code report an EPIPE hook error for inputs over ~64 KB. `HookSocket` reuses `MCPSocketListener` (folder 0700, socket 0600, same uid). A request is accepted only from a process descending from that tab's shell (peer pid ancestry), else "no decision": `SINGULARITY_TAB` is inherited by tmux/screen servers started in a tab, which would otherwise route questions from terminals outside Singularity into the inbox. The cost: Claude Code inside tmux/screen (or any multiplexer that daemonises) in a Singularity tab gets no level 2, in either terminal mode; it shows its own prompt, and level 1 works only as far as the multiplexer passes OSC through. The app acknowledges each request with one byte (0x06) from the main actor and the helper gives up after 5 s without it, so a hung app can't leave Claude Code on a spinner for an hour. At most 5 requests are held per tab; more get "no decision" at once. A question or permission is held up to 3300 s (`InboxCenter.holdLimit`), below the hook `timeout` of 3600 s (`ClaudeHookSettings.hookTimeoutSeconds`), then answered "no decision" (the prompt appears in the terminal) and the card becomes a plain waiting entry. The helper never half-closes its end: macOS reports a half-closed Unix socket exactly like a closed one, and the close is how the app learns that Claude Code killed the hook (Esc, Ctrl-C, quit), which removes the card. A held *permission* is also released when the tab's status becomes working/done/idle or `Stop` arrives (Yes in the terminal does not kill the hook; so answering one of several held permissions in the terminal hands the tab's others back too); a held *question* is not released by `working` (status is `working` while `PreToolUse` runs). A permission card shows the input's identifying fields first, one per line as `name: value` (`file_path`, `path`, `notebook_path`, `command`, `url`, `pattern`, `description`; for Bash the command first), then the rest as sorted JSON, cut at 4000 characters; when it was cut (`isComplete` false) the card says "Too long to show in full." and offers only Deny and Go to terminal, and `InboxCenter.decidePermission` refuses Allow for it from any caller: the owner must never approve what he can't see. A `PermissionRequest` for `AskUserQuestion` gets "no decision" at once and never an entry. `Stop`'s `last_assistant_message` is the done entry's text. Quitting hands every held request back to its terminal.
  - **The one config file Singularity writes: `~/.claude/settings.json`**, and only when the owner presses Install / Update / Remove on Settings → Agents → "Show questions in the inbox" (the exception to "agent config files are only read"). `ClaudeHookSettings` (Core, text in, text out) adds or removes only our three entries (recognised by the helper's file name as the command's first word), keeps everything else and refuses JSON it doesn't fully understand; rewriting sorts keys and respells some numbers (its header comment lists how). Each command is `'<helper>' 2>/dev/null || cat >/dev/null` (`ClaudeHookSettings.command`): Claude Code runs it in every session, also outside Singularity, so a missing helper (bundle moved or deleted, being rebuilt by `build-app.sh`, swapped by an update) must stay silent: no error message, stdin read to the end, exit 0. `.installed` means exactly what Install would write; a stale or partial install, or one written as the bare quoted path (before the guard), reads as not installed, so the button says Install and repairs it; Remove takes out both forms. `HookInstaller` refuses non-UTF-8 bytes, writes a temp file in the same folder and `rename`s it, keeps the file's mode (a new file gets 0600, a new `~/.claude/` 0700), writes *through* a symlink (dotfile managers), reads the file back and checks it, and never creates anything when only reading or removing. Which file: `SINGULARITY_CLAUDE_SETTINGS` if set, else `<SINGULARITY_HOME>/claude-settings.json` in a test copy, else the real one (`ClaudeHookSettings.file(environment:home:)`). The bare debug binary has no helper inside a bundle: the row says it needs the app bundle and offers no button; a translocated app gets no button either.
  - **The bare binary has no banners**: `UNUserNotificationCenter.current()` traps without a bundle identifier, so the notifier makes no backend then (counts and panel still work). Before every banner the notifier reads the notification setting and asks macOS only while it is undetermined (never at launch); a "no" is not remembered, so banners start once allowed in System Settings. It withdraws only the banners this process posted: a development copy shares the bundle id, and so the list of delivered banners.
- **Split view.** `Space.splits: [SplitGroup]`; a tab is in at most one. Arc-style: the content area shows the selected tab's whole split, or the tab alone; the sidebar shows a split as one row of chips. Every tab of a visible split is loaded. Things that bit us, keep them:
  - A tab's web/terminal view can only be in one place. During layout changes SwiftUI may update an outgoing pane next to the new one, so `HostedView` lets only the *newest* `PaneContainerView` own a view.
  - WKWebView takes almost any drop, so panes put a transparent `PaneDropOverlay` on top only while a tab is dragged (private UTI `dev.roosa.singularity.tab`, declared in Info.plist).
  - Pane headers sit in the window's invisible title-bar strip, where macOS starts a window drag before asking the view (`mouseDownCanMoveWindow` is not enough). `PaneDragHandleView` switches `window.isMovable` off while hovered. Never put SwiftUI `.help()` on chrome in that strip: it adds an overlay view that eats the click.
- **Plugins** (spec `docs/superpowers/specs/2026-11-09-plugins-design.md`, guide `docs/plugins/AUTHORING.md`). Plugin = folder in `~/Singularity/plugins/<id>` with `plugin.json`, optional `background.ts` (bundled Bun) and `page.ts`. Background runs under `sandbox-exec` with a generated SBPL profile (no network, reads its folder, writes its data folder) and a minimal env; programs only via `singularity.run` for declared commands at paths pinned at approval (`CommandPolicy.refused`). Every file is fingerprinted (dotfiles, node_modules; a top-level `.git` is skipped, and unreadable in the sandbox; symlinks and hard-linked files are refused); any change pauses the plugin until re-approved, except code edits in development mode; widened permissions and package files always need approval. Packages: exact registry versions + `bun.lock`, installed at approval with `--ignore-scripts` and `--omit=optional`, staged. Page scripts run in an isolated `WKContentWorld` after `PluginPrelude` (no network/eval/cookies/storage; frames still loading that the world can reach via `window[n]` are locked best effort, check with `scripts/probe-plugin-frames.sh`; real-click guards on buttons); DOM routes can't be blocked, so review matters. `FillGuard`: a fill needs frame host = `forHost` (or subdomain), `fillForms` match, and a genuine click. Don't loosen these without the owner.
- **Site settings and "console and network" for agents** (spec `docs/superpowers/specs/2026-11-10-devtools-site-settings-design.md`). Per Space and site (origin), in `space.json` (`Space.siteSettings`): camera/microphone Ask/Allow/Block (`WebTabController.decideMediaCapturePermissionsFor` → `MediaRules`), "Let agents see console and network", and plugins switched off for the site. WKWebView has no console/network API, so `PageCaptureScript` injects a collector into the *page's* world (wraps console.error/warn, fetch, XHR; failures only) plus a relay in our own content world that holds the message handler; both do nothing unless `location.origin` is a switched-on site, and `CaptureBridge` checks every message's sender against the switches again. Device choice and screen sharing were left out: WebKit has no public API.
- **TypeScript/TSX artifacts** (spec `docs/superpowers/specs/2026-11-10-ts-artifacts-design.md`). The artifact server compiles `.ts/.tsx/.jsx/.mts` on request: `transpile-artifact.ts` runs in the plugin sandbox on a *copy* of the file (`PluginPageCompiler.runHostScript`), one file in, one module out, imports left as written. `./util` also finds `util.ts` etc. (`ArtifactScripts.resolveModule`, same containment rules). A script opened as a page gets a small shell page (plus the folder's `importmap.json`); `app.tsx`/`index.tsx`/`main.tsx` open a tab by themselves only when their folder has no HTML page. Compile errors come back as a module that shows them. Still no API routes.
- **herdr-core terminals** (spec `docs/superpowers/specs/2026-11-11-herdr-core-terminal-design.md`). - **Plugin panels and programs** (spec `docs/superpowers/specs/2026-11-13-assistant-part1-design.md`, its "As built" section overrides the design; guide `docs/plugins/AUTHORING.md`). Two plugin abilities, built for the Assistant: a plugin's own page (manifest `panel: { page, title }`) shown in a native panel at the right of the main window (⌃⌘J, View menu, palette; width in `settings.json` as `pluginPanel`/`pluginPanelWidth`) or as a plugin tab (`TabKind.plugin(pluginID:)`), and one running program (`permissions.programs`, plus `programEnv`). Things to keep:
  - **The page is locked.** `PluginPageServer` serves it from the plugin's folder under `singularity-plugin://<id>/` (a `WKURLSchemeHandler`, not the artifact server: no port, no token, no Space), GET only, contained regular files only (`ArtifactFiles` rules), `.ts/.tsx` compiled like TS artifacts, bare imports through an import map built from the declared packages (`PluginImportMap`). An HTML entry must sit at the top of the folder (a script page may be in a subfolder). Every response carries a Content-Security-Policy (own origin only, a fresh script nonce per response, `connect-src 'none'`, `frame-src 'none'`, no inline script, no `eval`). `PluginPageHost`'s web view has a non-persistent data store; navigation off the origin, new windows, downloads, page dialogs, camera and microphone are refused; no page agent, capture or other plugins' scripts; no agent tool can list or read a plugin tab (`list_tabs` leaves it out, the other tools answer "not a web page"). Two holes were found and closed: after `tearDown` the page's JavaScript keeps running until its web view is released, and WebKit holds delegates weakly, so teardown hands the view to `ClosedPageGuard.shared` (lives as long as the app, refuses everything) instead of clearing the delegates; and the policy does not cover WebRTC, so `peerConnectionEnabled` is switched off by key (only after checking `_setPeerConnectionEnabled:` responds, else a document-start script removes `RTCPeerConnection` in every frame). Don't loosen these without the owner.
  - **The page's bridge.** `window.singularity = { send, onMessage }`, defined only when `location.origin` is the plugin's, and the native side takes only main-frame messages whose `securityOrigin` is the plugin's. `send` reaches the background's `onPageMessage` with `tabID: "panel"` and `frameHost: ""`, and is never dropped for a Space reason: a plugin with a panel runs whenever it is approved, and its Space switches show only when it also has a page script (or has no panel at all). `singularity.panel.post` from the background reaches `onMessage`; the JSON is passed as an argument of `callAsyncJavaScript`, never pasted into script text; posts are dropped until a page of ours has committed and queued (at most 1000) until the page sets a handler. 256 KB a message both ways.
  - **The page host changes identity.** `PluginManager.pageHost(for:)` makes the page only while the plugin is approved and running, and tears it down on every stop (paused, changed, removed, re-approved, development-mode restart); a crash restart keeps it and reloads it. So the page is never served while the plugin isn't running or its files aren't the approved ones, and a view must ask `pageHost(for:)` in its body every time and never keep a host or its web view. While a plugin isn't running, panel and tab show the native "<Title> isn't running" page with `PluginScan`'s status text and a button to Settings → Plugins.
  - **One page, one place.** A plugin has one page view. Open as Tab removes any other tab of that plugin and closes the panel when it shows that plugin; Move to Side Panel removes the tab; the panel stays hidden while that plugin's page is a tab, and the shortcut then selects the tab. The rules are pure (`PluginSurface`); `HostedView`'s newest-container rule keeps the one web view in one place. No panel in little windows or under the welcome flow; web-only commands (Find, Reload, Zoom, Print, the address row's site settings) are off for a plugin tab.
  - **The program bridge.** `singularity.spawn(program, args, { env })` in `host.ts` returns a Node-like child process; the app (`PluginProgram`, `PluginProcess`) starts the pinned path with `posix_spawn`, never a shell, in its own process group, in the plugin's data folder, inheriting only fds 0-2. The app builds the whole environment (`ProgramEnvironment.make`: the real `HOME`, `USER`, `LOGNAME`, the login shell's `PATH`, `TMPDIR`, `LANG`, `CLAUDE_AGENT_SDK_CLIENT_APP=singularity/<version>`), and of what the plugin passes only names listed in `programEnv` (which can never be `HOME`, `PATH`, `DYLD_*`, `SINGULARITY_*` and the like). One program per plugin; the pinned path is checked again at every start. Output comes with backpressure (at most about 1 MB the plugin hasn't read), more than 16 MB of input waiting ends the program, stderr goes to the plugin log. It ends with the plugin: SIGTERM to its group, SIGKILL 2 s later; at app quit SIGKILL at once, synchronously. The reaper waits with `waitid(…WNOWAIT)` and only then kills the group, so a group signal can never reach a recycled pid. Arguments are free: what keeps the Assistant without tools is its reviewed `provider-claude.ts` (it starts `claude` with no tools, settings, MCP servers or skills: `--tools= --setting-sources= --strict-mcp-config`, `skills: []`), not the app.
  - **Test and development copies start no programs.** `ProgramPolicy.spawnAllowed`: with `SINGULARITY_HOME` set, every start is refused with "programs are off in a test copy" (with the real `HOME` it would chat on the owner's account and write sessions into their real Claude folder), unless `SINGULARITY_REAL_PROGRAMS=1`. That switch is set by hand only, for the owner's hands-on checks; never by a script or a test run. Tests use the fixture program (`Tests/SingularityCoreTests/Fixtures/echo-program.sh`), passed in, not resolved from a manifest.
  - **Packages** of a plugin are installed with `--omit=optional` too (the Agent SDK's optional 329 MB copy of Claude Code is never installed; the SDK runs the user's own `claude`).
  - **Third known exception to "everything under `~/Singularity/`": Claude's own session files.** The Assistant continues a conversation by its session id; the session itself is a file Claude Code writes in its own config folder (`~/.claude/projects/…`, or the folder named in the Assistant's settings), which the plugin's sandbox can't read and doesn't need to. What the owner sees is kept in the plugin's data folder (`~/Singularity/plugins-data/assistant/conversation.json`, deleted by New Chat) and its settings in `storage.json` there. Removing the plugin's data does not remove Claude's session files.

A translocated app gets no button. The same rows are in Settings → Agents. - **Updates** (spec `docs/superpowers/specs/2026-11-12-updates-design.md`; Sparkle 2, one track, feed on GitHub Releases). Things to keep:
  - **Only release bundles update.** `release.sh` stamps `SUFeedURL` and `SUPublicEDKey` into the bundle's `Info.plist`; the checked-in `Resources/Info.plist` has neither (it has the static keys `SUEnableAutomaticChecks` true, `SUScheduledCheckInterval` 3600, `SUAllowsAutomaticUpdates` false: no "install automatically" choice, the owner always confirms). `UpdatePolicy` (Core, tested) decides: both keys present, `SINGULARITY_HOME` not set (unless the bundle carries `SGUpdateTestBundle`, which only `release.sh --scratch` sets) and not translocated. Anything else has no updater at all: `build-app.sh` bundles, bare debug binaries, test copies, `swift test` and `release.sh --skip-notarize`; the menu item and the Settings switch are disabled with a one-line reason. A test or debug build must never check for updates or replace itself. `AppUpdates` is the only file that touches Sparkle; it checks at launch and then hourly, and the switch is `AppSettings.checksForUpdates` (Settings → General, through `AppState.updateSettings`). System profiling stays off: a check is one HTTPS request that shows GitHub the IP address and the app's name and version.
  - **Feed and keys.** `SUFeedURL` is `https://github.com/karlijuhkam/singularity-browser/releases/latest/download/appcast.xml`: every release carries its own one-entry `appcast.xml`, and GitHub's "latest" always resolves to the newest. Releases are normal releases (never GitHub pre-releases, which "latest" skips), and the owner and repository name are baked into every installed copy, so they never change. The update key is an EdDSA pair: the private half lives only in the owner's login keychain (with a backup in their password manager; lose it and no installed copy can be updated again), the public half is `PUBLIC_ED_KEY` in `release.sh`. Never put it in the repository or run `generate_keys` without the owner. An update installs across a change of code-signing identity as long as the EdDSA key is the same (proved ad-hoc → Apple Development); a tampered zip is refused. Sparkle accepts only http or https feeds, never `file://`.
  - **`release.sh <version>` is draft-then-publish.** Checks, `scripts/test.sh`, version bump (`CFBundleShortVersionString` is shown, `CFBundleVersion` is a whole number that goes up by one and is what Sparkle compares), build, stamp, sign (notarized when the team has a Developer ID certificate and the `singularity-notary` profile, otherwise Apple Development and marked "not notarized"), zip signed with the update key, appcast, release notes (commit subjects since the last tag, edited in `$EDITOR`), a last look (version, build, notarized or not, certificate, notes; also shown on `/dev/tty` when stdout is not the terminal) and `Publish? [y/N]` asked and read on `/dev/tty` (`--yes` skips it; without a terminal a release needs `--yes`), commit "Release <version>" and push of the commit only, then a *draft* release gets the zip and `appcast.xml` and is published with `--latest`; publishing creates the tag, so installed copies only ever see complete releases. Step 1 also checks, read-only, that steps 7 and 8 can work: `origin` is `github.com/<REPO>` (`origin_is_repo`), gh's account may push and the repository is public (a private one would publish fine while every installed copy gets 404 on the feed), `git push --dry-run` works, and with `commit.gpgsign` on that git can sign. `release_commit_guard` runs after the tests, after the build and before the commit. A failure before the release commit (step 7) restores `Info.plist` and removes the zip, `appcast.xml` and notes it wrote in `dist/`; after the commit they stay, and the script prints the commands that finish it by hand (absolute `dist/` paths) and, while unpushed, the way back (`git reset --hard origin/main`). Running `release.sh <version>` again when "Release <version>" is HEAD and there is no tag prints the same commands instead of "not higher". The signing-identity lookup reads all of `security`/`openssl`'s output (`first_identity`): an awk `exit` on a pipe gets the producer killed by SIGPIPE under `pipefail`.
  - **Frameworks.** `scripts/embed-sparkle.sh` copies `Sparkle.framework` into `Contents/Frameworks/` and signs its helpers inside-out before the app is signed (never `codesign --deep`). Ad-hoc bundles (`build-app.sh`, and `release.sh --scratch`/`--skip-notarize` with `SIGN_IDENTITY=-`) get `Resources/Debug.entitlements` (library validation off) or the hardened runtime refuses the framework; a release never does (it refuses `SIGN_IDENTITY`). The SwiftPM artifact has no command-line updater (`.build/artifacts/sparkle/Sparkle/bin` has `generate_keys`, `sign_update` and friends only); the headless update test used Sparkle's own `sparkle-cli`, built from its source.
  - **The launcher starts its own bundle.** `singularity-mcp` starts the app it lives in by path (not by bundle ID, which the daily and development copies share), and while an update installer is running it waits and retries the socket rather than start a copy that would collide on the instance lock.
  - **Sparkle's preferences are a second known exception to "everything under `~/Singularity/`".** It keeps its small state (`SULastCheckTime`, `SUSkippedVersion`, its window frame) in the app's macOS preferences, `~/Library/Preferences/dev.roosa.Singularity.plist`. Every copy shares it with the real copy (same bundle ID), so in a test copy never click "Skip This Version": it would make the real copy skip that version.
  - **Not done on purpose:** more update tracks (stable/beta, see `IDEAS.md`), delta updates, silent installs, building on GitHub.
- **Little windows** (spec `docs/superpowers/specs/2026-11-12-little-window-design.md`). A web link from another app opens in its own small window (`AppState.openLink` → `LittleWindows.open`), one per link, never reused, with the logins and plugins of the Space that was selected then (its *home Space*). "Open in <Space>" (⌘O) moves the live page into the home Space as a tab without a reload, or loads the address again in another Space; closing leaves nothing. Things to keep:
  - **One registry, no tab.** The page is a normal `WebTabController` in `WebViewRegistry` (`littleController`), under an id no `BrowserTab` has, with `isLittle` set. So plugin scripts and `tabID(for:)` cover it, and moving it into its Space is just `adoptLittlePage`: add a `BrowserTab` with that id, `joinSpace()`, `showTab`. The little window's `LittleWebHost` adds the web view once and never takes it back, so the pane can have it.
  - **While `isLittle`:** no `webTabDidChange` (it would find no tab but still mark the Space dirty and rewrite `space.json`), no history entry, no favicon file; `createWebViewWith` loads in the same view (no pop-ups, so pop-up sign-in doesn't complete there); `window.close()` and a link that turns out to be a download (no page committed yet) close the window; `CaptureBridge` keeps nothing; no agent tool can reach it (tools go through a Space's tabs). `joinSpace()` records the visit and fetches the favicon that were skipped.
  - **Closing frees.** The window's content view holds the `LittleWindow` and it holds the window, so `dismantle()` (content view, toolbar, chrome) runs on every close and on the move, or the page would live on (`aClosedWindowIsFreedWithItsPage`). We take a window off screen with `orderOut`, never `close()`: closing the last window quits the app.
  - **Downloads outlive their window:** `WKDownload` holds its delegate weakly, so a controller keeps itself alive in `WebTabController.downloading` until its download ends (`downloadDidFinish`, `didFail`, or `DownloadCenter.cancel` → `downloadEnded`).
  - **Menu.** While a little window is the app's main window (`little.frontWindow`, from `windowDidBecomeMain`; not *key*: a sheet on it takes key, and ⌘W must still not reach the tab behind), page commands go to `AppState.frontController`, ⌘W (`closeTabCommand`) closes the window and never a tab, tab/split/sidebar commands and Open Location are off, and commands that go somewhere in the main window call `showMainWindow` first. The agent inbox belongs to the main window (`AppState.init`): its panel opens there, and a terminal counts as "looked at" only while the main window is key, not a little window.
  - **Main window.** `MainView` reports its `NSWindow` (`MainWindowReader`) and stores `openWindow(id: "main")` in `AppState.openMainWindow`. "Open in …" shows the main window *before* closing the little one: if the main window was closed, the little window may be the last, and closing the last window quits the app.
  - **Deleting a Space** closes its little windows first (`little.spaceWillBeDeleted`): their controllers are in no tab list, and WebKit won't remove a data store that is in use.
  - **Receiving links.** `AppDelegate` installs its own handler for the "open URL" Apple event in `applicationWillFinishLaunching` (it replaces AppKit's, so SwiftUI never reacts to the link with the main scene) and keeps `application(_:open:)` as the fallback; both feed `LinkInbox`, which holds links until the app state is attached (a link that starts the app). Only http/https.
  - **Only release bundles claim links.** Every bundle here has the same bundle id; if `build/`, test or scratch bundles declared http/https too, macOS could hand a link to a copy that isn't running, which exits on `InstanceLock` and the link is lost. So `Resources/Info.plist` has no `CFBundleURLTypes`; `release.sh` adds them in release mode only (`claim_web_links`, checked in `test-release.sh`). Settings → General → "Default browser" compares by bundle id (`DefaultBrowserRules`), names another copy that is the default, and offers "Make Default…" only in a bundle that claims links.
  - **In tests and trials:** never send a link through macOS (`open https://…` goes to the owner's daily copy) and never click "Make Default…" (it changes the owner's Mac; tests use `FakeDefaultBrowserSystem`). Tests call `state.little.open` with `staysOffScreen = true`; `SG_LITTLE_SNAPSHOT=<file.png> swift test --filter LittleWindowTests/snapshot` writes a picture of a little window with its title bar. A real link to a trial copy, without the default browser being involved and without taking focus: `open -g -n -a /private/tmp/sg-app/Singularity.app --env SINGULARITY_HOME=/private/tmp/sg-lw http://127.0.0.1:<port>/` (`-a` names the bundle, `-g` keeps it in the background, `-n` starts it; without `-n` a further link goes to that running copy), then look at its windows with `CGWindowListCopyWindowInfo` (this shell cannot take screenshots); quit it with SIGTERM and remove the bundle afterwards.
  - **Window size.** The frame is set *after* the toolbar and content view are in (the toolbar makes the window taller), and the minimum size is enforced in `windowWillResize`: the toolbar and the hosting view both overwrite `minSize`/`contentMinSize`.
- **Sidebar** (spec `docs/superpowers/specs/2026-11-13-sidebar-design.md`). The bottom row spans the whole sidebar, under the rail too: New Tab, New Terminal, then the launchers. Things to keep:
  - **Launchers** (`AppSettings.launchers`, Settings → Terminal; a file without the key gets Claude Code and Codex, an empty list stays empty). `AppState.openTerminal(launcher:)` goes through `newTerminal`, so folder, project and picker rules are New Terminal's; the picker's mode carries the launcher's id. The command is **typed into the tab's login shell** (PATH, aliases and shell functions apply; the prompt is there when the program exits), by `TerminalSession.typeInitialCommand` after `waitUntilReady`. It lives only in `AppState.pendingCommands` until `TerminalRegistry` makes the tab's first session, which takes it: never in `space.json`, never typed after a restart of the app or the shell or when a herdr-core tab finds its shell again. Settings holds the rows as typed (a half-typed row must not vanish); `AppState.launchers` is the cleaned list (`Launcher.clean`) and the only one to make buttons from. No agent tool, page or plugin can add or run one. The first four are buttons, the rest a menu. The logos are SVG text in `LauncherLogos` (Simple Icons, CC0; other companies' marks, used to name their programs).
  - **Space icon**: `Space.icon`, one emoji (`Emoji.single`, applied on decode and in `setSpaceIcon`), shown only in the rail.
  - **Width**: `AppSettings.sidebarWidth` (220…480, `SidebarLayout`). The width strip is the sidebar's last 6 pt (its own padding, never the page); it writes the setting on mouse-up and switches `window.isMovable` off while hovered, like `PaneDragHandleView`.
  - **Hidden** (`AppSettings.sidebarHidden`, ⌘S): the sidebar is the *same* `SidebarView`, moved off the left edge with an offset, so it keeps its scroll position; the page gets the whole window and the window's three buttons are hidden (`applyWindowButtons`). `SidebarEdgeTrigger` (in the 8 pt margin left of the page, `hitTest` nil) opens the slide-out; while it is out a 0.15 s timer reads the facts and closes it after two "no reason to stay" in a row. A timer, not mouse-exited events: those don't arrive while a menu or drag has the mouse. Rules: Core `SidebarPeek`. It stays while a mouse button is down (a tab dragged out of it), a menu is open, or the inbox panel hangs off its tray button; a drag never opens it. Off screen, the inbox panel opens at the window's corner (`InboxCenter.trayIsOnScreen`).
- **Settings window** (⌘,, SwiftUI `Settings` scene, `Sources/Singularity/Settings/`): General (search engine: `AppSettings.searchTemplate`, a URL with `%s`; "Default browser", see Little windows; "Check for updates automatically", the version and Check Now), Terminal (font, size, close on exit, launchers), Agents (all Spaces' agent switch + policy and "Activity…" via `AppState.updateSpace`, approval timeout, "Connect agents": the Connect/Update rows for Claude Code and Codex with the commands to copy, and under Claude Code "Show questions in the inbox" with Install / Update / Remove), Data & privacy (paths, per-Space clear history / site data / agent log). Stored in `~/Singularity/settings.json` (`AppSettings`, tolerant decoding); always change it through `AppState.updateSettings`.
- **Web tab basics** (`WebTabController`): `developerExtrasEnabled` (set by key) gives right-click → Inspect Element; a failed load shows `LoadErrorPage` (Core) via `loadSimulatedRequest`, so the address stays the failed one and Reload retries it; HTTP Basic/Digest sites get a login dialog (`.forSession` credentials, never the keychain); find in page is our own `FindBar` over `webView.find` (WKWebView has no find bar on macOS); zoom uses `pageZoom` and the `PageZoom` ladder. Camera and microphone need the two usage strings in Info.plist *and* the two entitlements in `Singularity.entitlements`; WebKit then asks per site.
- **Launch safety.** `InstanceLock` (Core): an `flock` on `<root>/.run/lock` taken in `SingularityApp.init` before `AppState` exists; a second copy on the same data folder activates the first and exits. `SpaceStore.load` skips a Space folder whose id is already loaded (a copied folder) and reports it; load errors are shown in an alert at launch (`AppDelegate.reportLoadErrors`), and unreadable files are never overwritten. Dialogs from pages (alert/confirm/prompt, HTTP login) are only shown for tabs that are on screen.
- WKWebViews are created lazily (only when a tab is first shown) and kept alive across Space switches.
- Later phases (see the brief): per-Space artifact server on 127.0.0.1 with a bearer token; MCP via a `singularity-mcp` stdio launcher → Unix socket at `~/Singularity/.run/mcp.sock`; approval policy + `agent-log.jsonl`.

## Build / run / test
No Xcode project: SwiftPM + scripts. The scripts need full Xcode (macOS 27 SDK; SwiftUI's `@State` macro plugin and current SwiftTerm both require it). Xcode is installed on the external drive at `/Volumes/Zealot/Xcode.app`. `scripts/env.sh` points builds at it with `DEVELOPER_DIR`. The system default stays on the Command Line Tools on purpose, so `git` keeps working when the drive is unplugged. **Do not run `xcode-select -s`.** Override the location with `XCODE_APP=…`.
- `scripts/build-app.sh`: builds, assembles and signs `build/Singularity.app` (ad-hoc, or `SIGN_IDENTITY=…`)
- `scripts/run.sh`: builds, then starts a **development copy** with its own data folder, `~/Singularity-dev` (or `SINGULARITY_HOME=…`; it starts empty and is never made by copying `~/Singularity`), as a new instance next to any other copy. It quits only a previous development copy, found by its exact executable path in this checkout's `build/` (SIGTERM, which the app turns into a normal quit: `quitOnSigterm`) **and** an absolute `SINGULARITY_HOME` in its environment (`ps eww`, read again for each pid right before its SIGTERM; `copy_decision` in `scripts/lib/dev-copy.sh`), never a copy elsewhere, and waits only for the pids it signalled. A `build/` copy without its own data folder, or whose environment can't be read, is the owner's daily copy on the real data (possibly a build from before `quitOnSigterm`): run.sh never signals it, stops before building (so its bundle is not replaced under it) and asks to quit it by hand. It also refuses a `SINGULARITY_HOME` that is not an absolute path (the app would ignore it and open the real data). Connect/Update and updates are off whenever `SINGULARITY_HOME` is set. Otherwise it still replaces `build/Singularity.app`, see the next point.
- **A full bundle next to the owner's running copy** (needed for anything that uses the bundled Bun: plugins, TS/TSX artifacts): `APP=/private/tmp/sg-app/Singularity.app scripts/build-app.sh`, then run its `Contents/MacOS/Singularity` with `SINGULARITY_HOME` as below. The owner's daily copy lives in `/Applications` (installed from a release since 0.2.0, 2026-11-12): it updates itself and nothing here touches it. Never run a daily copy from `build/`: build-app.sh replaces that bundle, and run.sh refuses to start while a `build/` copy runs on the real data.
- **Trying a build next to the owner's running copy:** `SINGULARITY_HOME=/private/tmp/sg-test .build/out/Products/Debug/Singularity` runs a second copy with its own data folder and agent socket (keep the path short: Unix sockets allow ~100 characters); drive it with `SINGULARITY_MCP_SOCKET=$SINGULARITY_HOME/.run/mcp.sock singularity-mcp`. Never quit the owner's copy for a test. Its terminals export its own hook socket, so Claude Code in them talks to the test copy. Its "Show questions in the inbox" row works on `$SINGULARITY_HOME/claude-settings.json`, never the real `~/.claude/settings.json`; to point it at another file set `SINGULARITY_CLAUDE_SETTINGS=/path/to/settings.json` (read only by `HookInstaller`'s default initialiser). A bare debug binary shows that row without a button; try Install with a full bundle in `/private/tmp/sg-app`. Plugin programs (the Assistant's `claude`) are refused in such a copy; `SINGULARITY_REAL_PROGRAMS=1` lets them run, on the owner's real account, and is for the owner's own hands-on checks only.
- `scripts/test.sh`: unit tests (Swift Testing), the offline tests of the agents' launcher (`test-launcher.sh`) and of the release scripts (`test-release.sh`; never reaches the network, `gh` or the keychain) and of run.sh's checks (`test-run.sh`; never runs run.sh), then `Vendor/bun/bun test Tests/plugins` when Bun has been fetched
- `RealAgentConnectTests` (opt-in, skipped by `scripts/test.sh`) runs Connect/Update with the real `claude` and `codex` through the login shell: `source scripts/env.sh && SINGULARITY_REAL_AGENTS=1 CLAUDE_CONFIG_DIR=/private/tmp/sg-agents-<new name> CODEX_HOME=/private/tmp/sg-agents-<new name>/.codex swift test --filter RealAgentConnectTests`. The two variables send both agents' config to that throwaway folder; the test refuses to run unless both have exactly that form, the folder is new (or marked as its own) and the login shell reports the same two paths, and it only removes the files the agents write there, so the real `~/.claude.json` and `~/.codex/config.toml` are never written.
- `RealAssistantTests` (opt-in, skipped by `scripts/test.sh`, run only when the owner chooses to) sends one message through the bundled Assistant with the real `claude`, on the owner's own account: `source scripts/env.sh && SINGULARITY_REAL_ASSISTANT=1 swift test --filter RealAssistantTests`. It copies `Plugins/assistant` to `/private/tmp/sg-ra-<8 hex>`, installs its packages there with the repository's Bun as approval does (needs the network), finds `claude` through the login shell as the approval sheet does, runs `background.ts` under the real `PluginProcess` with `programsAllowed: true`, and expects `ready` with a billing value, a piece of the answer and `ready` again within 60 s. It counts against the owner's Claude plan and leaves one short session in Claude's own folder; a throwaway `CLAUDE_CONFIG_DIR` can't be used, because that folder would be signed out. No window, no app. No other test or trial runs the real `claude`.
- `scripts/probe-plugin-frames.sh`: manual check (not in test.sh) after changing `PluginPrelude.swift`: runs the real prelude in a WKWebView against a local server and prints locked/UNLOCKED per frame-insertion route
- `scripts/release.sh <version>`: the one-command release (see Updates above): universal build → signing → (notarization → staple) → zip, appcast → `Publish? [y/N]` (or `--yes`) → GitHub release. `release.sh --skip-notarize` is a signed local build in `dist/` that publishes nothing and is not stamped for updates. `release.sh <version> --scratch <dir>` builds a throwaway update-test bundle with a throwaway key (`scripts/make-scratch-key.sh`, never the keychain) and a local feed served over http on 127.0.0.1; the test copy is never activated and gets no input. The header of the script lists every mode, flag and environment switch. Signing: **Singularity is signed by team `T748B76PPL` (Karli Juhkam, personal)**: the script only considers certificates whose OU is `TEAM_ID` (default T748B76PPL). This Mac also holds certificates of another company's team that must never sign Singularity. Identities are chosen by SHA-1 fingerprint (duplicate certificate names are ambiguous). Notarization needs a Developer ID Application certificate in team T748B76PPL and the `singularity-notary` notarytool profile, both set up by the owner.
- App icon: `scripts/icon/render_orb.py` is a numpy port of the orb shader on singularity.rroosa.ee; `make_icon.py` puts it on a macOS tile; `make_icns.sh` builds `Resources/AppIcon.icns` (white orb, dark tile). As on the site, the orb is white in dark mode and black in light mode: while running, `AppDelegate` swaps the Dock icon to `DockIcon-dark/-light.png`. `Orb-dark/-light.png` are only the fallback of the live orb now (see Onboarding). `Resources/*.png` are copied into the bundle.
- **Never run the real `claude mcp add/remove` or `codex mcp add/remove` in tests or trials, and never write `~/.claude.json`, `~/.claude/settings.json` or `~/.codex/config.toml`.** `HookInstaller` tests always pass a temp file (never `HookInstaller()` with its default). `AgentConnector` takes an `AgentShell` and a home folder, so tests pass a fake shell and a temp home (`AgentConnectorTests`). In a running test copy, don't click Connect or Update: they change the owner's real agents. To see what the real programs write, point them at throwaway `CLAUDE_CONFIG_DIR` / `CODEX_HOME` folders.
- Plain `swift build` in a fresh shell uses the Command Line Tools and fails. Run `source scripts/env.sh` first, or use the scripts.
- **Bun** (owner-approved dependency, runs plugins): `scripts/fetch-bun.sh` downloads the pinned version of both arch zips, verifies their pinned SHA-256s and lipos them into `Vendor/bun/bun` (git-ignored, ~100 MB). `build-app.sh` and `release.sh` call it, copy the binary to `Contents/Helpers/bun` and sign it with `Resources/Bun.entitlements` (JIT, needed by JavaScriptCore under the hardened runtime) before signing the app. To upgrade, change the version and both checksums in the script.
- The tab model is called `BrowserTab` because SwiftUI has its own `Tab` type.
