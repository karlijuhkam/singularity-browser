# Singularity Browser — guardrails for every session

A native macOS browser whose organising unit is the **Space**. The sidebar holds three kinds of tabs side by side: **web pages**, **terminals** (where the user's own coding agents run), and **locally generated HTML artifacts**. An *external* agent (e.g. Claude Code in a terminal tab) can drive the browser through an MCP server the app exposes. There is no built-in AI, no chat UI, no API keys.

## The scope rule
**If it is not a tab type, it is not in v1.**

If you want to add something that is not in the brief, write it to `IDEAS.md` under "New, not yet decided" instead of building it. Ask before adding any dependency not listed below.

## Explicitly out of scope for v1
Do not build, scaffold, or leave TODOs for:
sync of any kind · browser extensions (WebExtensions/WKWebExtension; Singularity plugins replace them) · built-in AI or chat UI (AI only inside plugins, round 2) · Windows/Linux/iOS · Peek/Little Arc-style windows · bookmarks beyond pinned tabs and folders · history UI beyond what the command palette needs · reader mode · ad blocking · themes · API routes on the artifact server · databases · an entity store · calendar/email/notes integration · agent orchestration (Herdr already does that; we only host terminals).

**Scope change (owner decision, after Phase 4):** tiling / split view is *in* v1, built before Phase 5: nested splits (any pane splits right or down), Arc-style split groups, created via context menu, drag and drop, keyboard and palette.

**Scope change (owner decision, plugins round 1):** Singularity plugins (not a tab type) are in v1; see the spec (`docs/superpowers/specs/2026-11-09-plugins-design.md`).

**Scope change (owner decision, 2026-11-10):** everything listed in `IDEAS.md` is approved to be built, except its sections "Decided against" and "New, not yet decided". `IDEAS.md` has the order and the rules (projects need an owner-approved design first; small items don't). Where an approved item overlaps the out-of-scope list above (e.g. the plugin storage API, download UI), the item in `IDEAS.md` wins; the rest of the list still holds.

## Hard constraints
- Swift + SwiftUI (AppKit where SwiftUI falls short). No Electron, no web-based app chrome.
- WKWebView only. macOS 14+, Apple Silicon first.
- No sync, accounts, telemetry. All data lives under `~/Singularity/`.
- Allowed dependencies: SwiftTerm (terminal), FlyingFox or Hummingbird (local HTTP server), the official MCP Swift SDK. Verify APIs before use; do not rely on memory.
- Boring, readable Swift. The owner reads TypeScript/PHP more fluently than Swift, so comment the non-obvious AppKit/WebKit parts.

Key decisions:
- **Space** = UUID, name, colour, slug (fixed at creation; renaming changes only the display name; the one exception is the welcome flow, see Onboarding), cwd. Each Space has its own `WKWebsiteDataStore(forIdentifier: space.id)`, so cookies and storage are isolated.
- **Not sandboxed.** Terminal tabs need to spawn login shells. Hardened runtime is on.
- On disk: `~/Singularity/state.json` (Space order and selection) and `~/Singularity/spaces/<slug>/{space.json, history.jsonl, favicons/}`. Writes are atomic and debounced.
- **Known exception to "everything under ~/Singularity/":** each Space's cookies, logins and site data live in WebKit's store at `~/Library/WebKit/dev.roosa.Singularity/WebsiteDataStore/<space id>/`. WebKit chooses that location and the app cannot move it. Consequences: copying `~/Singularity/` does not carry logins over; deleting `~/Singularity/` by hand leaves the cookies behind (deleting a Space in the app does remove them); and the stores are tied to the bundle ID, so **never change `dev.roosa.Singularity`**, or every Space starts logged out. Changing the signing identity is fine.
- **Artifact server auth (decided with the owner; the brief asked for a Bearer header on every request).** WebKit cannot add headers to page sub-requests, so: the app loads each artifact tab's first request with `Authorization: Bearer <token>`; the server answers that with `Set-Cookie: singularity_token=…; HttpOnly; SameSite=Strict`; sub-requests and `fetch()` then use the cookie. The token is random per Space per launch, never in files, never readable by page JS, and the cookie lives only in that Space's WebKit store. (Setting the cookie natively via `WKHTTPCookieStore` does not work: WebKit silently drops cookies for a bare-IP domain.) The server also refuses non-loopback Host headers (DNS rebinding) and sends no CORS headers.
- `window.singularity` exists only on the Space's artifact origin (the script checks `location.origin`, and the native handler checks the message's `securityOrigin`). `prompt()` always asks (native sheet), then bracketed-pastes into the Space's most recently used running terminal and presses Return. Phase 5 replaces "always ask" with the Space policy.
- **MCP.** Agents run `Singularity.app/Contents/MacOS/singularity-mcp` (stdio). It contains no MCP logic: the app runs an MCP `Server` (official Swift SDK) per socket connection, reusing the SDK's `StdioTransport` on the socket's file descriptor. Tools: `list_spaces` plus `<slug>.<tool>` for Spaces with `agentsEnabled` (per-Space toggle in Edit Space, off by default); `tools/list_changed` is sent when that set changes. Claude Code shows `work.read_page` as `mcp__singularity__work_read_page` (dots become underscores; verified). The socket folder is 0700, the socket 0600, and peers must have the same uid.
- **Page agent.** `PageAgentScript` is injected at document start into every web/artifact tab in an isolated `WKContentWorld`, so pages can't see or tamper with it. Refs come from a WeakMap (element → number) and are stable for the life of a page load. Everything page-derived that is returned to an agent goes through `UntrustedContent.wrap`. Agent-opened tabs load in the background (not selected) at 1280×800.
- **Approvals (Phase 5).** Every agent tool call and every `window.singularity.prompt()` goes through `AgentApprovals.check` *inside the app*, so the policy holds for any client (an agent once drove `singularity-mcp` directly). Rules live in `AgentApprovalRules` (Core, tested): reads always pass; readOnly refuses acting; allowAll passes; ask shows a sheet (Allow / Allow on <site> / Deny, 2-minute timeout = deny) unless the page's site was allowed, and **always** asks for form submissions, artifact prompts and going to a site not yet allowed. `click` inspects the element first (submits a form? link to another site?), and while a click/type runs `WebTabController.agentNavigationGuard` holds any navigation that wasn't approved. Every call is appended to `<space>/agent-log.jsonl` (password text never logged) and shown in the sidebar's Agent activity pane; tabs opened by agents carry `openedByAgent` (sparkles badge), tabs being worked on pulse. The approval timeout is a setting (`agentApprovalTimeoutSeconds` in `~/Singularity/settings.json`); set it to e.g. 5 for tests.
- **Split view.** `Space.splits: [SplitGroup]`; a tab is in at most one. Arc-style: the content area shows the selected tab's whole split, or the tab alone; the sidebar shows a split as one row of chips. Every tab of a visible split is loaded. Things that bit us, keep them:
  - A tab's web/terminal view can only be in one place. During layout changes SwiftUI may update an outgoing pane next to the new one, so `HostedView` lets only the *newest* `PaneContainerView` own a view.
  - WKWebView takes almost any drop, so panes put a transparent `PaneDropOverlay` on top only while a tab is dragged (private UTI `dev.roosa.singularity.tab`, declared in Info.plist).
  - Pane headers sit in the window's invisible title-bar strip, where macOS starts a window drag before asking the view (`mouseDownCanMoveWindow` is not enough). `PaneDragHandleView` switches `window.isMovable` off while hovered. Never put SwiftUI `.help()` on chrome in that strip: it adds an overlay view that eats the click.
- **Plugins** (spec `docs/superpowers/specs/2026-11-09-plugins-design.md`, guide `docs/plugins/AUTHORING.md`). Plugin = folder in `~/Singularity/plugins/<id>` with `plugin.json`, optional `background.ts` (bundled Bun) and `page.ts`. Background runs under `sandbox-exec` with a generated SBPL profile (no network, reads its folder, writes its data folder) and a minimal env; programs only via `singularity.run` for declared commands at paths pinned at approval (`CommandPolicy.refused`). Every file is fingerprinted (dotfiles, node_modules; a top-level `.git` is skipped, and unreadable in the sandbox; symlinks and hard-linked files are refused); any change pauses the plugin until re-approved, except code edits in development mode; widened permissions and package files always need approval. Packages: exact registry versions + `bun.lock`, installed at approval with `--ignore-scripts`, staged. Page scripts run in an isolated `WKContentWorld` after `PluginPrelude` (no network/eval/cookies/storage; frames still loading that the world can reach via `window[n]` are locked best effort, check with `scripts/probe-plugin-frames.sh`; real-click guards on buttons); DOM routes can't be blocked, so review matters. `FillGuard`: a fill needs frame host = `forHost` (or subdomain), `fillForms` match, and a genuine click. Don't loosen these without the owner.
- **Site settings and "console and network" for agents** (spec `docs/superpowers/specs/2026-11-10-devtools-site-settings-design.md`). Per Space and site (origin), in `space.json` (`Space.siteSettings`): camera/microphone Ask/Allow/Block (`WebTabController.decideMediaCapturePermissionsFor` → `MediaRules`), "Let agents see console and network", and plugins switched off for the site. The panel is the button at the right of the address row. Capture is **off unless switched on twice** (`Space.agentInspection` and the site's switch; `InspectionRules`); then `read_console` / `read_network` appear as tools. WKWebView has no console/network API, so `PageCaptureScript` injects a collector into the *page's* world (wraps console.error/warn, fetch, XHR; failures only) plus a relay in our own content world that holds the message handler; both do nothing unless `location.origin` is a switched-on site, and `CaptureBridge` checks every message's sender against the switches again. Everything captured is untrusted page content, lives in memory per tab (`PageCapture`), is never logged, and is dropped when the tab leaves the site or a switch goes off. These scripts and the per-site plugin switches are rebuilt by `PluginScripts` (it owns every content controller's user scripts: `spaceScripts`, `offSites`) and apply from a page's next load. Device choice and screen sharing were left out: WebKit has no public API.
- **TypeScript/TSX artifacts** (spec `docs/superpowers/specs/2026-11-10-ts-artifacts-design.md`). The artifact server compiles `.ts/.tsx/.jsx/.mts` on request: `transpile-artifact.ts` runs in the plugin sandbox on a *copy* of the file (`PluginPageCompiler.runHostScript`), one file in, one module out, imports left as written. `./util` also finds `util.ts` etc. (`ArtifactScripts.resolveModule`, same containment rules). No packages are shipped: bare imports go through the page's import map. A script opened as a page gets a small shell page (plus the folder's `importmap.json`); `app.tsx`/`index.tsx`/`main.tsx` open a tab by themselves only when their folder has no HTML page. Compile errors come back as a module that shows them. Still no API routes.
- **herdr-core terminals** (spec `docs/superpowers/specs/2026-11-11-herdr-core-terminal-design.md`). Settings → Terminal, off by default: the shell is started with the owner's installed `hc run --name sg-<tab id>` and the SwiftTerm view runs `hc attach` instead of the login shell, so shells outlive the app and a tab finds its shell again by name. Closing a tab ends the shell (`hc kill`/`hc rm`), quitting doesn't (`tearDown(endProgram:)`). The shell's pid comes from `hc get`; the foreground group from `proc_pidinfo`. Anything unexpected falls back to the built-in terminal. Test with `HC_SESSION=<name>` so the owner's own herdr core isn't touched.
- **Import from Arc** (spec `docs/superpowers/specs/2026-11-11-arc-import-design.md`): File → Import from Arc… reads `~/Library/Application Support/Arc/StorableSidebar.json` and makes new Spaces (pinned tabs, folders keep their nesting via `Folder.parentID`; within a folder the sidebar lists folders first, then tabs, optionally the unpinned tabs). No logins.
- **Plugin storage**: `singularity.storage` (get/set/delete/keys/clear) lives entirely in `host.ts`, as one atomically replaced `storage.json` in the plugin's data folder, which the plugin could write anyway. No new permission, nothing on the app side. Not encrypted: the guide and the review checklist say no secrets.
- **Small things from IDEAS.md**: "Show Tab" in the approval sheet (a button in the alert's accessory view, so it doesn't answer the question; restarts the timeout); an artifact tab whose file is gone is marked in the sidebar and shows a "file is missing" page until the file returns; downloads are listed in the sidebar (`DownloadCenter`, in memory); tabs can be dragged between Pinned, folders and Tabs (`Space.moveTab(_:to:atRow:)`, `onInsert` + drop targets on headers and folders); the artifact server answers `Range` requests.
- **Onboarding and the live orb** (spec `docs/superpowers/specs/2026-11-11-onboarding-design.md`). A four-step welcome flow (Welcome, Your first Space, Connect your agent, Plugins) replaces the whole window content while `AppState.onboarding` is set. Things to keep:
  - **When.** By itself only on a brand-new launch: `FirstRun.isBrandNew` = the store loaded no Spaces *and* reported no load errors, so `AppState.init` made the placeholder "Personal". **No "seen" flag is stored**: after that launch a Space exists on disk. A folder whose Space files are all unreadable gets the load-error alert, never the flow. Again on request: Singularity → "Welcome to Singularity…" and the palette (`showWelcome`).
  - **Leaving.** Skip setup, Esc and Start browsing call `closeWelcome`. Commands the user gives that go somewhere else close it first: `showPalette` (and the palette's own actions), `openTerminal`, `openArtifact`, `showTab` (the approval sheet's "Show Tab"), and the wrappers `userSelectSpace(_:)` and `showSpaceEditor(spaceID:)` (Space rail, Spaces menu, ⌘1…⌘9, palette, New/Edit Space). Things that happen without the user do **not** close it: `selectSpace` (`createSpace` and the Arc import call it while the flow must stay open; new user-facing Space pickers go through the wrappers), `openInNewTab` (an artifact page's `singularity.open`), agents' tabs, new artifact files. While the flow is open (`AppState.welcomeCoversWindow`) the menu commands that act on the hidden tab, page or sidebar are disabled (Find, Print, Reload, Back/Forward, Zoom, Next/Previous Tab, the split commands, New Folder) and ⌘W closes the flow, never the hidden tab (`Commands.swift`).
  - **The one slug exception.** Step 2's Continue (`applyWelcomeSpace`) gives a new slug only to the brand-new install's placeholder (`firstRunPlaceholderID`) while it has no tabs (`FirstRun.mayReslug`), so a Space named "Work" gets `work.read_page`, not `personal.…`: save, stop its artifact server, `SpaceStore.moveSpaceFolder`, `toolsChanged()`. The placeholder status ends at its first tab or when the flow closes; reopened from the menu, renaming changes only the display name. `ArtifactHosts.stop` also cancels a pending start (the launch's queued start used to recreate `spaces/personal/artifacts` after the move).
  - **Arc import** during the flow: the imported Spaces replace the placeholder only while it is untouched (no tabs, step 2's Continue never applied: `placeholderCustomised`), via `deleteSpace`, so its folder goes to the Trash. A placeholder the user already named stays, whether the import comes from the File menu on a later step or from step 1 after Back. Either way the flow goes on at step 3.
  - **Connect never starts a server and never edits a config file.** `AgentConnector` checks by *reading* `mcpServers.singularity.command` at the top level of `~/.claude.json` (per-project entries ignored) and `[mcp_servers.singularity]` in `~/.codex/config.toml` (a line scanner, no TOML library); anything unreadable or unexpected means "not connected". It never runs `claude mcp get`: that health-checks the entry, i.e. starts the registered `singularity-mcp`, which can start or reach another copy of the app (the owner's, during a `SINGULARITY_HOME` trial). Only on the user's click it runs `claude mcp add -s user singularity -- <launcher>` / `codex mcp add singularity -- <launcher>` (Update: `mcp remove` first; if the remove works and the add fails, the old entry is gone and the row shows the error), then reads the file again and shows what it says. Commands run through `AgentLoginShell` (`$SHELL -l -i -c`, cwd home, stdin /dev/null, 20 s timeout), because a Dock-started app has a minimal PATH, `codex` lives under nvm and `claude` can be a shell function; installed = `command -v` exits 0. A translocated app gets no button. The same rows are in Settings → Agents.
  - **Agents stay off.** Connecting never opens a Space: the step's "Let agents use …" switches start off and go through `setAgentsEnabled` (policy stays `.ask`).
  - **Bundled plugins.** `build-app.sh` and `release.sh` copy every `Plugins/*` except `template` to `Contents/Resources/Plugins/`, and `docs/plugins/AUTHORING.md` plus `Plugins/template/` to `Contents/Resources/plugin-guide/` (rsync without node_modules/.git/.DS_Store, before signing). Step 4 lists them (`BundledPlugins.list`; empty for a bare debug binary), so a new folder in `Plugins/` shows up with no UI change. Add = `PluginInstaller.add`, then the normal `PluginApprovalSheet`; never approve in code.
  - **The orb.** `OrbView(size:)` is an `MTKView` drawing a line-for-line Metal port of `render_orb.py` (the site's shader), in the flow and in the empty-Space placeholder. The MSL source is a Swift string compiled at run time with `makeLibrary(source:)` (`OrbShader.swift`): no `xcrun metal` build step, which SwiftPM wouldn't run anyway. 30 fps; white in dark mode, black in light; the pointer moves the ripple origin (10 % easing per frame). It **animates only while someone is looking** (`OrbAnimation.shouldAnimate`, a pure function with tests): its window is the key window, on screen and not covered, the app is not hidden (⌘H), Reduce Motion is off. The empty-Space orb (`OrbView(size:stopsWhenIdle: true)`) also stops after 30 s without the pointer moving over it, and moves again on pointer entry or movement, or when the window becomes key (the 30 s count restarts); the welcome flow's orb doesn't stop for that. Stopped, it holds its last frame. `isPaused` and `enableSetNeedsDisplay` are switched together. Under Reduce Motion it is one still frame. No Metal device or a shader that doesn't compile → `Orb-dark/-light.png` (keep those files). `OrbTests` compares frames with `render_orb.py` output (mean difference < 8 for white, < 2 for black: the GPU's float32 rounds `snoise`'s exact-zero cases the other way from numpy's float64).
- **Settings window** (⌘,, SwiftUI `Settings` scene, `Sources/Singularity/Settings/`): General (search engine: `AppSettings.searchTemplate`, a URL with `%s`), Terminal (font, size, close on exit), Agents (all Spaces' agent switch + policy via `AppState.updateSpace`, approval timeout, "Connect agents": the Connect/Update rows for Claude Code and Codex with the commands to copy), Data & privacy (paths, per-Space clear history / site data / agent log). Stored in `~/Singularity/settings.json` (`AppSettings`, tolerant decoding); always change it through `AppState.updateSettings`.
- **Web tab basics** (`WebTabController`): `developerExtrasEnabled` (set by key) gives right-click → Inspect Element; a failed load shows `LoadErrorPage` (Core) via `loadSimulatedRequest`, so the address stays the failed one and Reload retries it; HTTP Basic/Digest sites get a login dialog (`.forSession` credentials, never the keychain); find in page is our own `FindBar` over `webView.find` (WKWebView has no find bar on macOS); zoom uses `pageZoom` and the `PageZoom` ladder. Camera and microphone need the two usage strings in Info.plist *and* the two entitlements in `Singularity.entitlements`; WebKit then asks per site.
- **Launch safety.** `InstanceLock` (Core): an `flock` on `<root>/.run/lock` taken in `SingularityApp.init` before `AppState` exists; a second copy on the same data folder activates the first and exits. `SpaceStore.load` skips a Space folder whose id is already loaded (a copied folder) and reports it; load errors are shown in an alert at launch (`AppDelegate.reportLoadErrors`), and unreadable files are never overwritten. Dialogs from pages (alert/confirm/prompt, HTTP login) are only shown for tabs that are on screen.
- WKWebViews are created lazily (only when a tab is first shown) and kept alive across Space switches.
- Later phases (see the brief): per-Space artifact server on 127.0.0.1 with a bearer token; MCP via a `singularity-mcp` stdio launcher → Unix socket at `~/Singularity/.run/mcp.sock`; approval policy + `agent-log.jsonl`.

## Build / run / test
No Xcode project: SwiftPM + scripts. The scripts need full Xcode (macOS 27 SDK; SwiftUI's `@State` macro plugin and current SwiftTerm both require it). Xcode is installed on the external drive at `/Volumes/Zealot/Xcode.app`. `scripts/env.sh` points builds at it with `DEVELOPER_DIR`. The system default stays on the Command Line Tools on purpose, so `git` keeps working when the drive is unplugged. **Do not run `xcode-select -s`.** Override the location with `XCODE_APP=…`.
- `scripts/build-app.sh`: builds, assembles and signs `build/Singularity.app` (ad-hoc, or `SIGN_IDENTITY=…`)
- `scripts/run.sh`: build, then quit any running copy and launch
- **A full bundle next to the owner's running copy** (needed for anything that uses the bundled Bun: plugins, TS/TSX artifacts): `APP=/private/tmp/sg-app/Singularity.app scripts/build-app.sh`, then run its `Contents/MacOS/Singularity` with `SINGULARITY_HOME` as below. Never run plain `scripts/build-app.sh` or `scripts/run.sh` while the owner's copy runs from `build/`: they replace that bundle.
- **Trying a build next to the owner's running copy:** `SINGULARITY_HOME=/private/tmp/sg-test .build/out/Products/Debug/Singularity` runs a second copy with its own data folder and agent socket (keep the path short: Unix sockets allow ~100 characters); drive it with `SINGULARITY_MCP_SOCKET=$SINGULARITY_HOME/.run/mcp.sock singularity-mcp`. Never quit the owner's copy for a test.
- `scripts/test.sh`: unit tests (Swift Testing), then `Vendor/bun/bun test Tests/plugins` when Bun has been fetched
- `RealAgentConnectTests` (opt-in, skipped by `scripts/test.sh`) runs Connect/Update with the real `claude` and `codex` through the login shell: `SINGULARITY_REAL_AGENTS=1 CLAUDE_CONFIG_DIR=/private/tmp/sg-agents CODEX_HOME=/private/tmp/sg-agents/.codex swift test --filter RealAgentConnectTests`. The two variables send both agents' config to that throwaway folder (the test refuses to run unless both point inside /private/tmp that way), so the real `~/.claude.json` and `~/.codex/config.toml` are never written.
- `scripts/probe-plugin-frames.sh`: manual check (not in test.sh) after changing `PluginPrelude.swift`: runs the real prelude in a WKWebView against a local server and prints locked/UNLOCKED per frame-insertion route
- `scripts/release.sh`: universal release build → Developer ID signing → notarization → staple → `dist/`. `--skip-notarize` signs with the team's Apple Development certificate. **Singularity is signed by team `T748B76PPL` (Karli Juhkam, personal)**: the script only considers certificates whose OU is `TEAM_ID` (default T748B76PPL). This Mac also holds certificates of another company's team that must never sign Singularity. Identities are chosen by SHA-1 fingerprint (duplicate certificate names are ambiguous). Notarization needs a Developer ID Application certificate in team T748B76PPL and the `singularity-notary` notarytool profile, both set up by the owner.
- App icon: `scripts/icon/render_orb.py` is a numpy port of the orb shader on singularity.rroosa.ee; `make_icon.py` puts it on a macOS tile; `make_icns.sh` builds `Resources/AppIcon.icns` (white orb, dark tile). As on the site, the orb is white in dark mode and black in light mode: while running, `AppDelegate` swaps the Dock icon to `DockIcon-dark/-light.png`. `Orb-dark/-light.png` are only the fallback of the live orb now (see Onboarding). `Resources/*.png` are copied into the bundle.
- **Never run the real `claude mcp add/remove` or `codex mcp add/remove` in tests or trials, and never write `~/.claude.json` or `~/.codex/config.toml`.** `AgentConnector` takes an `AgentShell` and a home folder, so tests pass a fake shell and a temp home (`AgentConnectorTests`). In a running test copy, don't click Connect or Update: they change the owner's real agents. To see what the real programs write, point them at throwaway `CLAUDE_CONFIG_DIR` / `CODEX_HOME` folders.
- Plain `swift build` in a fresh shell uses the Command Line Tools and fails. Run `source scripts/env.sh` first, or use the scripts.
- **Bun** (owner-approved dependency, runs plugins): `scripts/fetch-bun.sh` downloads the pinned version of both arch zips, verifies their pinned SHA-256s and lipos them into `Vendor/bun/bun` (git-ignored, ~100 MB). `build-app.sh` and `release.sh` call it, copy the binary to `Contents/Helpers/bun` and sign it with `Resources/Bun.entitlements` (JIT, needed by JavaScriptCore under the hardened runtime) before signing the app. To upgrade, change the version and both checksums in the script.
- The tab model is called `BrowserTab` because SwiftUI has its own `Tab` type.
