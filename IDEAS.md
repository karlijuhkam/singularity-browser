## Approved, but blocked outside the project

- **Ghostty as the terminal engine.** Approved, but it cannot be built sensibly yet. Last checked 2026-11-10: `libghostty-vt` 1.0.0 (2026-11-06) is the only stable library; it is the emulation core (parser, screen state, key encoding) with no drawing, fonts or PTY. The API that has those (`include/ghostty.h`) calls itself internal, for Ghostty's own macOS app only, with no stability promise. A Swift framework "that handles the entire terminal view" is planned without a date. So building on it would still mean writing our own renderer, and SwiftTerm already covers all of that. Before starting, check again whether Ghostty ships a stable embeddable terminal *view*. If it does, build it; if not, leave this item and tell the owner.

## New, not yet decided

Nothing here gets built without an explicit decision from the owner.

- **Setup export and import (the browser's setup in the owner's own git repository).** Raised 2026-11-13: the owner changes laptops often and wants Spaces, pinned tabs, folders, projects, settings and plugins back in minutes, also on two Macs side by side; open tabs stay per machine. Parked by the owner 2026-11-13 as a future idea. Draft design, not approved, with open questions for the owner: `docs/superpowers/specs/2026-11-13-setup-export-design.md` (export and import by menu into a folder, the owner runs git). It is sync, so approving it is a scope change.
- **The app running git on the setup folder.** The step after the item above: commit, pull and push from inside Singularity with the owner's installed `git` and keys, and a per-Space choice on a conflict. Needs the app to remember the last synced state so removals travel by themselves. Not designed.
- **Sessions that follow the owner (open tabs across machines), as a web service.** Raised 2026-11-13; the owner wants this kept out of the git setup. Open tabs change every minute, so it needs a service and real merge rules, and it reverses "no sync, accounts". Not designed.
- **A Linux version.** Raised 2026-11-13 (not Windows). It is a second app rather than a port: SwiftUI/AppKit, WKWebView (per-Space data stores, content worlds), SwiftTerm's view, Metal, Sparkle and `sandbox-exec` are all Mac-only; WebKitGTK is the nearest engine. What could carry over: `SingularityCore` (not yet checked to build on Linux; e.g. `ProcessInspector` won't), the file formats, the MCP tools, the Bun plugin host. Reverses "Windows/Linux/iOS" in the out-of-scope list and the Swift/WKWebView hard constraints. Until then: keep the setup folder's format free of Mac-only things.

- **Left out of the sidebar work** (`docs/superpowers/specs/2026-11-13-sidebar-design.md`, built 2026-11-13): Arc's Space icons in the Arc import; a mark for waiting agents while the sidebar is hidden (the counts live on the rail); a tab dragged to the left edge pulling the hidden sidebar out; launchers in splits, per Space, or with their own shortcuts.
- **Left out of little windows** (`docs/superpowers/specs/2026-11-12-little-window-design.md`, built 2026-11-12): a setting to skip the little window and open links from other apps straight in a tab; little windows for links clicked *inside* Singularity (Peek); pop-up sign-in inside a little window (pop-ups load in the same window there, so a sign-in that needs its opener doesn't complete; opening the page in a Space works); opening local HTML files from Finder.
- **React shipped inside Singularity, for TSX artifacts.** TS/TSX artifacts are built (`docs/superpowers/specs/2026-11-10-ts-artifacts-design.md`) but ship no packages: a TSX page that uses React needs an import map pointing at files next to it or at a CDN. Bundling React (MIT) would make `app.tsx` work with nothing else, and is a new dependency, so it waits for the owner. Arbitrary npm packages would need the plugins' "declared and pinned" rule.
- **Arc favourites and split views in the Arc import.** The import (`docs/superpowers/specs/2026-11-11-arc-import-design.md`) leaves out Arc's favourites (they belong to an Arc profile, not a Space) and turns a split view into plain tabs. Both could be mapped if the owner misses them.
- **Console and network for artifact tabs.** `read_console` / `read_network` only cover web tabs (as designed). Agents that build artifacts would get a lot from seeing their own page's errors; the artifact origin changes port on every launch, so it needs its own switch rather than a per-site one.
- **Cross-engine checks by agents (instead of shipping more browser engines).** Raised 2026-11-11: the owner wants an agent to check their own work in other engines and say what broke. Embedding a second engine was considered and not chosen: on macOS it means Chromium via CEF, which would need a second implementation of everything built on WebKit APIs (page agent, plugin prelude, console/network collector, per-Space data stores, navigation guard), its own security updates, and breaks "WKWebView only". The cheap route needs no app code: an agent in a terminal tab runs Playwright (Chromium, Firefox, WebKit) against the dev server, collects console errors, failed requests and screenshots, and writes an HTML report into the Space's artifact folder. Limits: those browsers don't have the Space's logins, and Playwright's WebKit/Firefox are its own patched builds (the Singularity tab is the truer Safari check). Not tried yet; spike it first. Possible app features if the spike shows repeated friction: a `check_engines` agent tool, a built-in report view, or attaching to the user's installed Chrome over CDP (Chrome DevTools Protocol) for real console/network data.
- **More update tracks (stable / beta / nightly).** Updates are built with one track (`docs/superpowers/specs/2026-11-12-updates-design.md`). More tracks need a multi-entry feed (so the newest stable stays listed next to a beta) and a Settings choice for which track a copy follows.
- **Device choice and screen sharing in site settings.** Left out of the site settings panel: WebKit has no public API for either (see the "As built" section of `docs/superpowers/specs/2026-11-10-devtools-site-settings-design.md`). Revisit if WebKit adds one.
- **Agent state on terminal tab rows.** The agent inbox (`docs/superpowers/specs/2026-11-11-agent-inbox-design.md`) left out a mark on terminal rows in the sidebar (waiting, done, working); the inbox and the rail counts carry it instead. Could follow if the owner misses seeing it in the tab list.
- **The inbox hook as a Claude Code plugin.** Today Singularity writes its three hooks into `~/.claude/settings.json` behind a button, which rewrites the file (keys sorted). The design asked to check whether a Claude Code plugin installed with `claude plugin …` could carry the same hooks without touching that file; this was not looked into while building. Worth a spike before more people use the button.
- **Hermes in the inbox.** Hermes sends nothing the inbox can see unless `display.bell_on_prompt` / `display.bell_on_complete` are switched on in `~/.hermes/config.yaml` (both off on the owner's Mac). Settings → Agents could say so, or Singularity could leave it to the owner.

## Decided against

Do not build. Kept so the question isn't reopened without new facts.

- **Web-extension compatibility.** Decision: native plugins instead. Spikes in Nov 2026. Safari: the 1Password Safari extension wasn't usable in a WKWebView app; PlugInKit found 0 plugins, so there is no native messaging. Chrome: the 1Password Chrome extension under WKWebExtension lacked APIs (e.g. `chrome.notifications`), and shims weren't enough. So Singularity plugins (`docs/plugins/AUTHORING.md`) replace extensions.
